Expeditions, shard layers, travel, team sharing and role layouts

These tools are in the separate UO Assistant window. They use the GPU game client's ordinary controls and loaded observations. They do not replace shard rules, movement timing, travel restrictions or the server's assistant policy. A saved setting never starts an agent or travel action on login.

Expedition & recovery

The assistant notices a fresh alive-to-dead transition and saves a private death record with location, facet and time. A character already dead when connecting is treated as a baseline; reconnecting does not create duplicate deaths. Up to 64 death records are retained. Add a note to the selected death or show its destination on the native map.

Save healer locations explicitly while standing at the healer. The assistant does not infer resurrection service from a mobile's artwork or name. The list sorts same-facet locations by nearby tile distance. Its compass direction and tile count describe a destination, rather than a verified traversable route.

To make a numbered expedition route:

  1. Enter a route name and choose New empty route.
  2. At each stopping point, enter a waypoint name and choose Append current waypoint.
  3. Select a numbered waypoint to show it on the map, plan a nearby route, or explicitly walk to it.
  4. Use Stop walking, the client's normal movement controls or Stop all to interrupt owned movement.

There are at most 64 saved routes and 128 waypoints per route. Removing a waypoint preserves the order of the remaining ones. These are saved directions; the assistant does not automatically walk a whole expedition route or teleport between facets.

Set return point here preserves one homeward destination. Show current short trail puts recent points on the native map. The trail has at most 256 positions, is held in memory, and resets on disconnect/session change; the displayed sample uses the most recent 128 positions. Showing the trail replaces the current assistant marker overlay, so apply your saved map layers again to restore them.

The nearby planner searches only loaded terrain inside its bounded region. Unknown tiles are not assumed walkable. The result can account for the terrain and obstacles loaded by the client; it cannot prove that an unloaded area is traversable or that a shard will accept a step. A route preview starts no walking. Doors, mobiles, changing obstacles and server corrections can invalidate any client-side plan.

Shard layers & coordinates

First save a Shard label and use Fingerprint map folder to choose that shard's client-data folder. This reads map/static file names, lengths and samples of their first/last 64 KiB on a background worker. It does not change game files or copy them into the assistant. The resulting sampled fingerprint identifies a map-data set; it is not a full integrity hash of every byte. After updating custom maps, compute a new binding and review the affected layers explicitly.

A versioned map layer contains a schema version, permanent layer ID, revision number, shard label, sampled map fingerprint, markers and optional polygon zones. The assistant accepts a layer only when its shard and fingerprint match this profile. An existing layer can be replaced only by a higher revision with the same ID. This prevents an old downloaded pack from silently replacing a newer one. Export and remove existing layers before changing the profile's shard/map binding; review them against the new data before importing them again.

Choose Create layer from marker library to turn points already imported on Map library & terrain preview into an exchangeable layer. That page supports compatible CSV, UOAM .map and Ultima Mapper marker XML data; no external mapper program or icon archive is required. Export a selected versioned layer as JSON to share the data you choose.

For a JSON layer import:

  1. Optionally enter category mappings such as Shops=Services;Banks=Services.
  2. Choose Preview layer JSON. Review marker/zone counts, duplicate counts, sample point names and whether it replaces an earlier revision.
  3. Choose Apply reviewed layer to save the reviewed data privately.
  4. Choose Apply visible layers to game map to update the native map overlay.

Duplicates are compared by name, category, facet and coordinates. Duplicate points are skipped in the preview; the rest are imported as a single reviewed layer. A failed import applies none of the candidate points. Toggle a layer's visibility or remove it as required. Undo last layer edit keeps up to eight earlier layer states in memory; it restores layers without reverting unrelated death records, routes, travel presets or other assistant definitions.

Each layer has at most 2,048 markers and 64 polygon zones. A polygon needs 3–128 vertices on one facet. To draw a zone, choose a layer, enter its name/category, capture the current location at each corner, then save the zone. This increments that layer's revision. The page reports which visible zones contain the character, and applied zones appear as outlines on the native map. The native overlay accepts at most 256 visible markers, 64 zones and 4,096 total polygon vertices at once; hide layers to stay within those limits.

Custom sextant coordinates

Do not assume a custom shard uses standard Britannia coordinates. Enter and save that facet's map width, height and origin tile. Obtain those values from the shard's map author or verify them against known points. The initial editor values are examples until explicitly saved; no standard origin is automatically assigned.

Enter latitude degrees/minutes with N/S and longitude degrees/minutes with E/W. Degrees and minutes must be finite, minutes are from 0 up to but excluding 60, latitude is at most 90 degrees and longitude at most 180 degrees. Coordinates wrap inside the saved map dimensions. Show sextant destination creates a map destination using that saved facet origin; it does not start movement.

Runebooks & travel

Runebook layouts vary between shards. Learn the real loaded dialog instead of copying a historical button number:

  1. Pick an accessible book from your inventory, then open it through the game or Open selected book.
  2. Choose its loaded gump and a captured button. Add optional required text that identifies the expected page, then choose Add selected captured button.
  3. For a book with local page navigation, select its captured Open page choice and add that step first. Use Open selected local page to visit it manually, then add the actual recall/gate button from the new page. Repeat for any additional page/reply stages in their real order. Local page changes use an exact fresh dialog lease and send no server reply; the next server button must be captured at the resulting new revision.
  4. Set any shard-specific minimum mana and resource quantities. Optionally require literal loaded book-property text for a charge/status check. Property text is a literal check; the assistant does not guess the shard's charge formula.
  5. At a known destination, save the current location as an arrival coordinate. This allows arrival confirmation; without it, the run stops after dispatching the configured replies.
  6. Name, preview and save the destination. Explicitly start it with Travel to saved destination or a bound travel hotkey.

Every stage waits for a newly observed exact gump instance/revision and checks that the configured button is present. A changed, ambiguous, incomplete or missing dialog stops the run. The book must remain loaded, accessible, unprotected and in your inventory. Missing mana/resources, an active target/held item, movement, death or a session change also stops it. The assistant never reuses a saved gump token.

Failure messages are literal system-text fragments separated by |; edit them for your shard's language and wording. A matching fizzle/blocked/charge failure stops without retry. With an arrival coordinate, the assistant observes the same character near that point for a bounded period. A cross-facet arrival can be observed after the final reply, but no further action is dispatched across that world/session fence. No observed arrival means the outcome remains unconfirmed; no second travel request is sent automatically.

The runebook editor supports 128 named destinations, 16 reply stages and 16 resource checks per destination. It has no built-in spell/charge exploit or special shard packet. Existing shard restrictions and the assistant's stop controls still apply.

Team map & help pings

The page first shows members supplied by the shard's party system. Loaded health/position facts are shown when known; a member outside loaded range remains unknown. The native world map can also show party positions supplied by the shard itself.

An optional authenticated relay extends voluntary sharing between participating users. It is off every time the assistant opens. The application creates no external service or cloud deployment, and makes no sharing request until you explicitly connect.

Enter the relay root address, room, public label and private sharing secret. HTTP is accepted only for loopback; other addresses require HTTPS. The secret is entered in a password field, used in memory, cleared from the field after connecting and never stored in assistant preferences. Choose whether to share known health/death status; location and your chosen label are the basic shared fields. Accounts, passwords, inventory, game chat and shard credentials are not transmitted.

Updates run on a background worker about once a second, with one request at a time and a short timeout. Slow/offline sharing cannot hold up game input or rendering. A peer older than five seconds is marked stale, and health older than 15 seconds is hidden. Help, rendezvous and marker pings expire after 30 seconds. Select a member or ping to show its last shared destination on the game map; this starts no movement or targeting. Treat shared coordinates as voluntary reports from other participants rather than server authority.

Choose Stop sharing / disconnect to end sharing immediately. It also ends when the assistant closes or the paired game exits. A temporary disconnect pauses sending until fresh character state is available; the page continues to label stale observations.

Hosting the optional relay

UOAssistant.TeamServer is a separate optional administrative tool. The game never launches it. It stores no accounts or files; room members and pings exist only in memory. Limits are eight rooms, 64 members per room, 128 pings per room, bounded requests, eight concurrent requests and at most two updates per second from one client ID. Inactive members expire after 60 seconds.

Give the relay a random secret of at least 32 printable characters. Use a different secret for each team/service and distribute it privately. Everyone who knows the relay secret can participate, so replace it if a member should lose access. It is a shared-secret service, not an account/permission administration system.

For a local test on Windows, open a terminal deliberately for this optional tool, navigate to its folder and run:

$teamSecret = Read-Host -AsSecureString 'Team sharing secret'
$env:UO_ASSISTANT_TEAM_SECRET = [Net.NetworkCredential]::new('', $teamSecret).Password
.\UOAssistant.TeamServer.exe --listen http://127.0.0.1:9696/
Remove-Item Env:\UO_ASSISTANT_TEAM_SECRET

The relay reads the secret only from the process environment. Do not put it in command-line arguments, public scripts, screenshots or published packages. Press Ctrl+C to stop. If Windows refuses an HTTP listener, an administrator must reserve the exact chosen listener for the account or configure an HTTPS binding; the tool does not request elevation or alter firewall settings automatically.

For remote users, an administrator must provide an HTTPS endpoint and certificate, either directly on a configured Windows HTTPS listener or through an HTTPS reverse proxy to the loopback listener. Keep the underlying HTTP listener private, do not disable TLS certificate validation and do not expose an unauthenticated forwarding endpoint. This release does not deploy or configure hosting for you.

Developers can build the relay from the matching public source:

dotnet publish src/Assistant.TeamServer/Assistant.TeamServer.csproj -c Release -r win-x64 --self-contained true

Role layouts

Use named role presets for healer, crafting, combat or exploration work. Capture current layout saves the assistant dimensions/topmost setting/current section, game client dimensions, presentation settings and identities/positions of currently open movable game windows. It does not capture container contents, accounts or remote dialog tokens.

Select a role and review its preview, then explicitly apply it while stationary and with no active assistant run. Only uniquely matching windows already open in this character session are repositioned. Missing/ambiguous windows are skipped; containers are not reopened and server dialogs are not replied to. Positions are clamped into the chosen client bounds. The assistant remains a separate window, with its own screen position kept visible.

Undo last application restores the layout captured before the last application. Undo is held in memory until the assistant closes. Neither applying nor undoing a role logs in, casts spells, starts tasks or enables an agent. Up to 32 role presets can be saved. A role is a workspace/presentation preset, rather than an automatic gameplay loadout.

Verification and remaining live checks

The mapping/travel/team tests use synthetic map/state fixtures and an authenticated loopback relay. They cover death transitions and stale sessions, bounded trails, custom sextant validation, layer binding/revisions/duplicates/categories/polygons, settings ownership, exact fresh travel leases, no retry after a fizzle, observation of a cross-facet arrival, relay authentication/rate/expiry, actual background HTTP exchange and sampled map fingerprinting. They do not use a real account, shard or world save.

Live shard checks still matter for the particular runebook pages/messages, charge text, custom map origins, movement/collision corrections, remote HTTPS deployment, window placement at different DPI settings and the visible native map overlays. Only use a shard's permitted assistant functions.
